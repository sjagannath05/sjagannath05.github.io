The deploy repo is the state, and everything else is a convention

Twenty-four wireless services are deployed from one repository, where a release is a merged commit that changes an image version.

DevOps

What a deploy is

A service here is any directory holding a meta-dev.yml (twenty-four of them), alongside a meta-prod.yml. Between them they carry the image version, the squad, the maintainers and the promotion rules. For the host-based services they also carry the inventory groups to deploy to. A deploy is therefore a diff, and Git holds the intended state of production — which is convenient right up to the moment you want to know whether production agrees.

Two kinds of service live side by side. Some are Kubernetes workloads with a deployments/k8s/ tree of kustomize overlays (one overlay per environment). The rest are containers on dedicated hosts, started by Ansible, carrying host_groups in the meta file instead of overlays. Nothing declares which kind a service is — the files are the only signal. It is inferred from what files exist (a deployments/k8s/ directory, or host_groups in the meta file).

Automated changes still get a pull request

Ansible and AWX jobs write back into this repository. An unreviewed commit landing on main straight from a job run was the thing to prevent. So a push to ansible-auto-commit (and later any awx-job/* branch) triggers one workflow whose only job is to open the pull request:

on:
  push:
    branches:
      - ansible-auto-commit
      - 'awx-job/*'

Both actions in it are pinned to commit SHAs, not tags, each with the release it corresponds to in a comment above it. That was a same-day follow-up to the workflow itself (1 July 2024). It is also the cheapest supply-chain control available to a repository that hands a token write access to its own default branch.

A CLI that hardcodes nothing

The second piece is service-deployer/deploy.sh — 808 lines of shell, 27 commits under one ticket, February 2026. It discovers services, clusters and hosts from the config files that already exist. Any list it kept of its own would be wrong within a week.

./service-deployer/deploy.sh list
./service-deployer/deploy.sh <service> <env> [version|host_group]
./service-deployer/deploy.sh verify <service> <env>
./service-deployer/deploy.sh hosts <service> <env>
./service-deployer/deploy.sh status <service>

verify is the subcommand that earns the file. For a Kubernetes service it reads k8s_clusters from the meta file as kubectl context names, and the namespace from kustomization.yaml. It then queries every cluster (one kubectl call per context) and compares the running image against the version the repo claims. For a host-based service it resolves host_groups against an Ansible inventory (synced daily into service-deployer/inventory/). Then it SSHes to each host and reads docker ps (image tag per container, compared the same way).

The commit sequence is a list of assumptions being taken out. Read the namespace from kustomization.yaml instead of hardcoding it; read the clusters from the meta files; use kubectl in place of the internal CLI. Then: handle a service with no overlays directory; detect the deploy type from workflow filenames when the deployments directory is empty; parse host_groups without yq. One commit fixed a crash — piping a multi-line value through a shell variable lost it, so that step writes a temporary file and reads it back.

What I operate and did not write

The Kubernetes services are reconciled by ArgoCD, which the infra team runs. I live in it instead of building it. That means checking sync and health state, reading pod logs through it, working out why an application has drifted from Git, resyncing it, triggering a redeploy. Operating a platform leaves no commits behind (nothing to point at in a diff) and is still most of the day.

The Ansible side is someone else's design too. The autodeploy inventory is a literal docker create … && docker network connect … && docker start per service, with every environment variable spelled out. My seventy commits in it are variables and host groups: memory limits for the DRA and STP containers (12g hard, a 600m reservation), a log persistence mount for the STP logs, the resolver variables, point codes, external link ports.

The number I do not have

There is no deployment success rate in this repository, because nothing records one. deploy.sh status lists recent workflow runs for a service (via the gh CLI, newest first), and that is the closest thing to a measurement anywhere in the system. I believe deploys got faster and safer, and that belief is the only evidence I have. I cannot show you the series, so what I can describe is the mechanism and nothing about the outcome.

What is measurable is narrower and still worth saying. Every change to production is a reviewed diff in one repository. Every automated change arrives as a pull request. One command (verify) answers whether what is running matches it.
