The address plan that lives in a YAML comment

One Ansible variable file per site, two registers of IP addresses inside it, and nothing that checks either one against the other.

Automation

One Ansible variable file per site, two registers of IP addresses inside it, and nothing that checks either one against the other.

Two registers, one file

Each wireless site is a single group_vars file, and all of it hangs off one key (cloud_router_cluster_config). The files are not small: 443 lines for the EU Central site, 686 for US Central. Every tanker gets a map of VRFs, and every VRF gets a bridge subnet plus a list of containers to attach to it (name, address, one filter flag — nothing else).

vrfs:
  CORE:
    bridge_subnet: "172.22.8.0/24"
    preset_containers: []
      # Non-peering IP allocation:
      # .1 to .50 and .101 to .150 are allotted to the application vendor
      # IPs .51 to .60 are allotted for DRA
      # 172.22.8.51/24      wireless-dra-partner-a
      # 172.22.8.52/24      wireless-dra-partner-b
      # IPs .61 to .70 are allotted for DNS
  VRF_WL_PARTNER_B:
    bridge_subnet: "172.22.9.0/24"
    preset_containers:
      - name: "partner-b-proxy"
        ip: "172.22.9.2"
        apply_net4_rfc1918_filter: false

The first VRF is the one that matters, because its list is empty (preset_containers: []) and twenty-odd comment lines sit indented underneath it. Those comments are the address register — which host owns which address, which ranges belong to which team — and Ansible reads none of them. The list below it (preset_containers, with entries) is what actually gets a bridge interface. So one file carries a document and a program describing the same subnet, and only one of the two runs.

apply_net4_rfc1918_filter: false is set on every container, and that one line explains the estate. The interconnects carry private space end to end (172.22/16 on both sides), so the RFC1918 ingress filter is disabled per interface, not per router.

The register drifted inside one commit

CW-2557 expanded Partner A capacity in EU Central, and the diff is small enough to read whole (seventeen added lines, four of them comments). The comment block named the new proxies partner-a-proxy-3 and partner-a-proxy-4. The containers added to that partner's VRF in the same diff are partner-a-proxy-4 and partner-a-proxy-5. The two registers disagreed by one before the change reached a router at all — a bookkeeping failure, not a deployment failure. Nobody notices that kind until somebody greps for a name a year later.

CW-2256 is the same pattern with a bigger diff (US Central, April 2025, one file). Fifty added lines in the US Central file, of which thirty-nine are comments and nine are three container entries (one in the internet VRF, two in the partner breakout VRF). Counting changed lines and reporting them as provisioned addresses overstates that commit by roughly ten to one.

Drift from the other direction

CW-1256 is the honest commit in the set (November 2024, three commits squashed into one pull request). It cut five VRFs and ten GRE tunnels from one APAC tanker that had no containers in any of them (six VRFs defined, preset_containers: [] on all six). A third commit squashed into the same pull request came from the infra team, titled "update repo with manual VRF changes made in the tanker". The VRFs had already been taken off the box by hand; the repository was catching up with the router, not driving it. That is the direction this kind of codebase fails in, and no amount of YAML prevents it.

The automation that is actually there

One workflow, twenty-six lines, added in March 2026 — the only CI file I put in that repository. A push touching either alert file calls a shared reusable workflow twice (once for dev, once for prod) with secrets: inherit and an unpinned @latest reference.

on:
  push:
    branches: [main]
    paths:
      - "meta-dev.yml"
      - "meta-prod.yml"
  workflow_dispatch:

What it ships is thinner than the pipeline shipping it. The production file is alerts: {}, because its one container-down alert had moved to a dedicated alerts repository days earlier. The only alert left anywhere in the repo is in dev (frr_new_file_found == 1, held for ten minutes). It fires when a router's running FRR config stops matching what the templates render (a drift detector, named FrrConfigDriftDetected). Someone on the network team wrote that alert; I wired the path that deploys it.

There is no checkpoint-and-rollback framework here, no compliance scanner, no generated topology document. The playbooks render router configuration from these files — people do the rest. The one lesson worth keeping is narrow: a register kept in comments will disagree with the config beside it, and the only real fix is to delete the comment and let the config carry the meaning.
