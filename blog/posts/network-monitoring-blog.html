The host went down three times and the dashboard showed nothing

Losing a production host for five hours changed no line on any graph, because a dead target stops reporting instead of reporting zero.

Losing a production host for five hours changed no line on any graph, because a dead target stops reporting instead of reporting zero.

What the probes actually are

Monitoring for these services is CloudProber configs checked into the deploy repo, one per host, at <host>/probe/cloudprober.cfg (8 config files, 20 probe blocks). Almost none of them are TCP probes — the type is EXTERNAL throughout. They are EXTERNAL probes running the tool that speaks the protocol: ping -I <local-addr> bound to the right source interface for Diameter and M3UA peers, and gtping -c 1 -g 2 for the GTP proxies and the redirector. A TCP connect to 3868 proves only that a socket is listening; a GTP echo request proves the tunnel endpoint will answer, which is the thing subscribers depend on.

Each probe carries additional_label blocks (dest, ip_dest, probe_name, partner), so the resulting Prometheus series group by partner and by destination without string surgery in the query. Intervals are 5000ms for Diameter and M3UA peers and 30000ms for the GTP path. There is a constraint in CloudProber worth knowing before you tune anything: timeout_msec cannot be shorter than interval_msec, so halving one means halving both (both went 30000 to 5000 on one customer's out-of-band gateway after a proxy was added in the APAC region).

One probe was wrong for three weeks. The redirector's GTP ping was sourced from the proxy's address, one digit off, so it tested a path that was already covered and left the redirector unmeasured. Fixing it meant changing the gtping -s argument and the ip_src_addr label — the command decides what is tested and the label decides what the dashboard believes was tested.

Migrating the HSS Diameter and M3UA probes to the replacement HSS was the same exercise at scale. The old platform's association table (SCTP, Diameter on 3868, six M3UA associations on 2905-2911 plus two more on 8449) is where the probe list came from; the new config dropped 172 lines and added 94.

The outage that was invisible

In February 2026 one production host went down three times inside 48 hours: 55 minutes, 55 minutes, then five hours (all three windows overnight UTC). It hosted the IMS DRA (ims-dra-1-health) along with the node, audit and service exporters. Nobody was paged and no graph moved.

Four reasons, all structural:

  • No absent() panel. When the host died its series stopped arriving, so its line left the graph. No data is not a red line.
  • Aggregation hid it. Panels summed across hosts — and 48 of 49 hosts sum to roughly the shape of 49.
  • No host count. count(up{job="node-exporter", instance=~"infra-wireless-.*-aws-.*-prod"} == 1) going 49 to 48 is the cheapest outage detector available, and it was on no panel.
  • No alerts to fire. Nine services had no alerts: section in meta-prod.yml at all (three DRA flavours, two STP flavours, four IMS components), so the IMS DRA going away triggered nothing by design. Only wireless-manager carried a full alert catalogue (opsgenie and two Slack channels), and that is a Kubernetes service somebody else maintains.

That last one is the real finding. The dashboard gap is a dashboard problem; a service with no alert rules is a service nobody agreed to be woken for.

What the second dashboard does differently

The replacement is a 708-line Grafana JSON pointed at the long-term metrics datasource (imported by upload, not provisioned). It leads with a host liveness state timeline (green and red per host, so a gap is visible as red) and a host-count panel with a per-site breakdown. Consul service health is shown per datacentre instead of summed, so one site losing its IMS DRA reads as 1 to 0. Resource panels are per instance, filtered by a site variable.

Then the first version of it got the metric names wrong, which is the only way to find out what a service actually exports. Checking against the live datasource turned up 47 gtp_proxy_* series, diameter_peer_status and the diameter_*_routed counters for the DRAs, osmo_stp_active_asps_total and osmo_stp_as_up for the STPs, and billing's per-host record counter. The fleet naming matters too (infra-wireless-<site>-aws-<nn>-prod, 49 hosts across four sites), because every regex in the dashboard depends on it.

The second commit was larger than the first: 648 lines changed against 708 added. A dashboard written from the architecture diagram is a guess, and a dashboard written from the metric list is a measurement.
