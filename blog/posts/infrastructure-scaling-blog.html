Scaling by one gateway at a time

Adding capacity to the wireless estate meant adding two addresses per container to one YAML file, which is duller and more fragile than it sounds.

Infra

Adding capacity to the wireless estate meant adding two addresses per container to one YAML file, which is duller and more fragile than it sounds.

The unit of growth

A new packet gateway on a tanker costs exactly two addresses (one peering, one not). The peering address sits inside the partner's VRF; the other sits on the core bridge, where the gateway is reachable for management and metrics. Both are written into the same site file. The peering one goes into preset_containers, which Ansible acts on; the non-peering one goes into a comment block, which is the register and nothing more.

VRF_WL_INTERNET:
  bridge_subnet: "172.22.146.0/29"
  preset_containers:
    - name: "partner-c-pgw11-6"
      ip: "172.22.146.4/29"
      apply_net4_rfc1918_filter: false

That is the whole shape of it — three lines, one of them a flag. The smallest commit I made to this repository (CW-1186, October 2024) added one line to each of two site files, for one gateway in EU Central and one in APAC. The largest (CW-2256, April 2025) added fifty lines to one file, and three of those were containers.

The register had the same address twice

CW-1902 moved one proxy and one gateway onto a third tanker in US Central. Reading the register to find free addresses turned up two collisions already sitting in it (both in the same comment block).

-            # 172.22.152.3/24   partner-d-ch2-partner-c-pgw11-5
+            # 172.22.152.4/24   partner-d-ch2-partner-c-pgw11-5
-            # 172.22.152.8/24   partner-d-ch2-partner-c-proxy-5
+            # 172.22.152.9/24   partner-d-ch2-partner-c-proxy-5

Both addresses had already been claimed by the host listed above them (.3 by pgw11-4, .8 by proxy-4), so the register had been assigning one address to two hosts for months. It never caused an outage, because the register is a comment and nothing acts on it; it would have caused one the moment anyone provisioned from it. A move forced somebody to read the file, and reading the file is the only test it has (no linter, no schema, no CI check).

The same commit left a second mark. The container moved onto the third tanker kept the name it had on the second one (partner-c-proxy-7, among siblings named for a different tanker), so the name no longer says where the thing runs.

Deletion by commenting out

CW-2786 migrated two proxies from one partner to another in EU Central. The old entries were not removed — they were commented out in place, with a note above them, and the non-peering addresses were reused under new names in the other partner's VRF.

    # below proxies are migrated to Partner A
    # - name: "partner-b-proxy-2"
    #   ip: "172.22.9.6"
    #   apply_net4_rfc1918_filter: false

That is the house style, and it has one real virtue — the address stays visibly taken. It also means the file grows monotonically, so a 443-line site file describes rather less than 443 lines of running infrastructure.

What I cannot tell you

Nothing in this repository measures anything. There is no deployment counter, no uptime series, no record of how long a capacity expansion took or whether traffic dipped while it landed. The one alert defined anywhere in the repo watches for router config drift, and it is wired to dev (production's alert map is empty). So the honest account of thirty-three commits is a count of commits — four production sites, eight months, one YAML key — and an address register that was wrong twice in a way only a careful reader would find.
