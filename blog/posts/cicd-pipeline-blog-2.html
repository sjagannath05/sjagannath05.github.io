Splitting a VoLTE IMS into three builds, and the five passes it took

The IMS repository shipped one image containing every CSCF, a DNS server and a MySQL instance, and unpicking that into three independently built components took longer than writing any of them.

DevOps

What "one image" meant

The Makefile built six tags (build, mysql, dns, icscf, pcscf, scscf) and then one more:

# For backward compatibility - build the monolithic image
build-monolith:
    docker build --build-arg BUILDKIT_INLINE_CACHE=1 -t $(IMAGE_NAME) -f Dockerfile .

push-all pushed all seven (six split images plus the monolith). That is the honest state of a split: the new images existed, the old one still shipped, and both were built on every commit because something downstream had not moved yet. The Jenkinsfile was a shared-library block with custom steps bolted on — make build-all, then make build-monolith, then make push-all.

make test printed No test (one line, a tab and an echo). It still does.

The monorepo split

On 2 July 2025 the tree became ims/, dns/ and mysql/, each with its own Dockerfile, Makefile, Jenkinsfile and meta-dev.yml/meta-prod.yml, over a shared common.mk. 79 files touched, 779 insertions (most of it file moves). Most of the diff is file moves, and the one component that needed real thought was MySQL: its data is persisted on the IMS host, so the split had to hand a stateful container its own lifecycle without changing where the bytes live.

Jenkins to GitHub Actions, in five passes

The February 2026 migration is three workflows of seventeen lines each. They differ by two values only — a path filter and a build directory:

on:
  push:
    branches: [main]
    paths: [ims/**]
jobs:
  docker-image:
    uses: <shared>/.github/workflows/dockerImage.yml@latest
    with:
      build_dir: ims
      image_additional_tags: red
    secrets: inherit

Net effect: 97 lines added, 118 removed, the root Jenkinsfile and three per-service ones gone. The pull request took five passes to get there, and the sequence is the interesting part.

Add an -oci suffix to the service names; remove the -oci suffix. Add deploy stanzas (tankers_use_deploy_role: false, plus host_groups for dev and prod); remove the deploy stanzas, because they belong in the deploy repository and not in the source one. Restore the promote_to_dev config (branch pattern and all) that the first pass had dropped. Two follow-ups after the merge: image_additional_tags wanted a plain string where I had given it a JSON array, and promote_to_prod: always had to be set for all three services.

None of that is a pipeline problem. It is a boundary problem — which file owns the fact that this service deploys to those hosts — and every pass was me discovering the boundary was somewhere else.

What the pipeline does not do

Both vulnerability gates are off in meta-dev.yml:

allow_vulnerable_code: true
allow_vulnerable_image: true

The migration also deleted the Semgrep workflow (23 lines, gone with the Jenkinsfiles). So the scans are advisory here, and a post claiming this pipeline blocks on HIGH findings would be describing some other repository. Deployment is not in it either: the build promotes an image, and the deploy repository takes it to the wireless_ims_dev and wireless_ims_prod host groups. I operate that side daily without having written it.

Where the engineering actually went

Making the three CSCFs observable was harder than making them build. Kamailio has no metrics endpoint until you give it one, so each config loads xhttp and xhttp_prom, sets xhttp_prom_stats=all, and adds an event_route[xhttp:request] that serves /metrics and only /metrics, on a port of its own:

PCSCF_METRICS_PORT | default('8081')
SCSCF_METRICS_PORT | default('8082')
ICSCF_METRICS_PORT | default('8083')

The line that made it work is none of those. It is tcp_accept_no_cl=yes, which lets Kamailio accept an HTTP request carrying no Content-Length over TCP — which is exactly what a GET /metrics from a scraper looks like. Without it the listener is up, the port answers, and every scrape is dropped.

The base image moved from plain Ubuntu to the same FRR base the DRA and DNS images use (CW-2856, October 2025), which brought the templated resolv.conf and an FRR startup script into the IMS container and removed its hand-maintained resolver config.

Five services, three build triggers, no tests, and a metrics port that needed a parser flag (tcp_accept_no_cl). That is the pipeline.
