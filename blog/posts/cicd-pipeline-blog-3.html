The CI for a network service, when the pipeline is not yours to write

The DNS service for the private PGWs has a two-line Dockerfile and a ten-line Makefile, and its entire delivery pipeline is a handful of declarations in YAML that somebody else executes.

DevOps

What is in the repository

FROM coredns/coredns:1.11.1
EXPOSE 11915/tcp

That is the image (two lines, no local layers, nothing compiled). VERSION holds 1.11.1 to match, and the Makefile is three targets:

SERVICE_NAME:=$(shell cat meta-dev.yml | grep service: -m1 | cut -d ':' -f2 | xargs)
VERSION := red
IMAGE := registry.internal/jenkins/$(SERVICE_NAME):${VERSION}

build:
    docker build -t ${IMAGE} .
test:
    echo "no tests"
push:
    docker push ${IMAGE}

Shelling the service name out of meta-dev.yml looks like showing off and earns its keep: the image name and the service metadata cannot drift apart, because there is only one copy of the name. The test target has printed no tests since the first commit (16 July 2024) and still does.

The pipeline is a declaration

Under Jenkins the whole build was two lines — a shared-library import (pinned to @latest, which is its own kind of trust) and a dockerImage { } block. The library belongs to the platform team, so the repository declares which shape of thing it is and the library decides what that means. After the February 2026 migration it is a reusable workflow call instead, triggered on push and pull request to main plus workflow_dispatch:

jobs:
  docker-image:
    uses: <shared>/.github/workflows/dockerImage.yml@latest
    secrets: inherit
    with:
      image_additional_tags: red

Sixteen lines in the file, and none of them is a build step. Promotion is declared in the same spirit, in meta-dev.yml:

build:
  allow_vulnerable_image: true
  promote_to_dev:
    mode: always
    branch_pattern: "main|deploy-dev/.*"
  promote_to_prod:
    mode: always

meta-prod.yml is two lines; it carries the service name and nothing else. Ownership lives in the same file as the promotion rules (squad, primary_maintainer, secondary_maintainer), which means the thing that decides who gets asked about a failed build is a YAML key, reviewed like any other change.

The flag that tells the truth

allow_vulnerable_image: true is the honest line in that file. The scan still runs; its findings simply stop being blocking. For an image that is an upstream release pinned at 1.11.1, with no local layers to patch, the alternative is bumping upstream on the scanner's schedule instead of the service's — and that is a decision about the gateways, not about the build.

Semgrep is a second workflow, on a weekly cron (28 4 * * 0) in a returntocorp/semgrep container, skipped for dependabot. Its push trigger fires only on changes to the workflow file itself, so it is a scheduled scan and never a per-commit gate.

What that leaves

The whole delivery surface is under fifty lines of YAML and Make, and the one genuinely hard afternoon in it had nothing to do with testing or security: the new build wanted a previous image as its cache source, and for a repository Jenkins had only ever built under a different tag convention, that image did not exist. Four commits to break the cycle (bootstrap, revert, revert, delete). I wrote that up separately.

What CI buys a two-line image is narrow and worth being clear about. A digest that something other than a laptop produced, a tag that promotion can refer to (red first, promoted onward), and a record of who to ask. It does not buy confidence that the image works, and for this service nothing in the repository ever claimed it did.
