What the alert file actually says about reliability

Two YAML files, 295 alerts and one hardcoded Unix timestamp: the reliability apparatus for a wireless core, described honestly.

Infra

No SLO objects live in this repository, no error budgets, no burn-rate rules. There is meta-prod.yml (3,318 lines) and meta-dev.yml (706), each a flat map of alert name to five fields:

  DRAInstanceDown:
    description: "Diameter Routing Agent {{ $labels.job }} on {{ $labels.instance }} is down"
    destination: "opsgenie"
    prometheus_expression: 'min(up{job=~"(partner-c|partner-a|partner-b)-dra-[12]-metrics"}) by (job, instance) == 0'
    prometheus_for: 2m
    resolution_document: 'https://app.getguru.com/card/czBLE57i/DRAInstanceDown'

destination is the severity model in its entirety. 209 of the 295 alerts in production route to Opsgenie and page someone; 86 go to a Slack channel and only sit there. There is no third tier (no ticket queue, no digest), and tuning noise is almost all work on that one field.

Certificate expiry is a literal

The etcd cluster behind the wireless config store has three certificates in its chain (node and client, intermediate CA, root CA), and none is scraped. So the alert reads no metric at all:

  # This certificate for wireless-etcd nodes and client expires on 2026-01-13
  # The alert triggers 1 month before the certificate expiration, on 2025-12-13
  Node and Client Certificate Expiring for Wireless etcd service:
    description: "SSL certificate used by wireless-etcd service is about to expire and should be renewed"
    prometheus_expression: "vector(time()) >= 1765584000"
    prometheus_for: "1m"
    destination: "opsgenie"

Three went in together — CW-1832, January 2025 — node and client one month ahead, intermediate CA thirteen months ahead, root CA two years ahead. The root CA expires in 2055, so vector(time()) >= 2620339200 sits in the file waiting until 2053. The weakness is obvious: renew a certificate early and the literal goes stale, with nothing to detect the drift. It replaced no monitoring at all, and each comment carries the real expiry date, so the next person can check it by reading.

The silence that broke the alert

Two partner DRAs were provisioned but carrying no traffic yet, so DiameterPeerDown was paging on peers nobody intended to be up (two of them, neither yet in service). The fix I pushed (CS-1287, 17 October 2024) added job exclusions to the existing peer matcher:

min(diameter_peer_status{peer!="…", peer != "…", job != "partner-a-dra-[12]-metrics,job != "partner-b-dra-[12]-metrics"}) == 0

Two defects in one line — and the file still parsed. The quote after the first job name never closes, so the second exclusion is swallowed into the string; and != compares a label to a literal, where a bracket expression needs !~. Even written correctly it would match nothing. A colleague stripped the alert to a bare destination: "opsgenie" four hours later (07:19 UTC to 11:58 UTC), and that is how it still sits — an alert name with no expression, which at least fails visibly.

The lesson is about where the matcher lives. Editing a fleet-wide expression to silence two instances puts per-instance state into the one thing meant to be invariant — Alertmanager has silences for this, with an expiry date an edited expression never carries.

A rename is an outage in the detector

The unified DRA deployment changed the scrape job names, and the alert went from job=~"dra-metrics-partner-c-[12]" to job=~"partner-c-dra-[12]-metrics" in a one-line commit (CW-1287, October 2024). One line is the whole ticket — and it matters far more than its size. The old expression was sum(up{...}) < 2, and sum() over an empty instant vector returns no samples (not zero), so the comparison is never true. A down-detector whose selector stops matching goes quiet, which looks exactly like health.

The current form fixes the shape as well as the names: min(up{...}) by (job, instance) == 0 yields one series per instance, and the description interpolates two labels (job, instance), so the page names the host before anyone opens a dashboard.

Tuning is mostly deletion, and sometimes reversal

Four tickets in one week of November 2025 did the same thing four times — CW-2849 through CW-2852. Disk IO ops over 2000 and over 2700, CPU load over 70%, memory available under 20%, disk free under 10%. Each had a paging copy in production and a Slack copy in dev; in every case the paging copy went and the Slack copy stayed (moved to #wireless-infra-alerts). The disk threshold was loosened from 5% to 7% at the same time. A threshold a healthy tanker crosses on a normal Tuesday is not a monitor; it is a metronome.

The reverse happens too. 64 lines of LBO alerts for one site came out on 30 April 2026 and went back on 1 May, unchanged (a revert of the revert). Nothing about them was wrong; the decommission they anticipated had not happened.

What the windows look like

prometheus_for is the only real defence against flapping, and the distribution across production is lopsided on purpose — 129 alerts at 5m, 67 at 10m, 28 at 1m, 12 at 20m, 11 at 3m, 9 each at 15m and 1h, 7 at 2m, 4 at 30m. Seventeen declare no window at all and fire on the first evaluation. The 1m group is mostly inventory and latency alerts, where a single sample is already the answer; one alert sits at "1s", which nobody has explained to me.

Session-drop alerts get the longest windows (10m, mostly), because they compare against themselves:

( sum(avg_over_time(xcore_smf_pdnsession{...}[5m]))
  / clamp_min(sum(avg_over_time(xcore_smf_pdnsession{...}[1h] offset 1h)), 1) ) < 0.85
and
avg_over_time(xcore_pgw_count{...}[5m] offset 10m) >= 10

clamp_min(…, 1) keeps the denominator off zero; the and clause requires a baseline of at least 10 sessions, so an idle site cannot page anyone by dropping from 2 to 0. That second clause is the part that gets forgotten — it is the difference between a ratio alert and a pager that fires every Sunday morning.
