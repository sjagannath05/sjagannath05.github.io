What a carrier integration looks like from the routing side

Bringing a roaming partner up was mostly address allocation and one VRF per partner, with the Diameter work happening in somebody else's repository.

Bringing a roaming partner up was mostly address allocation and one VRF per partner, with the Diameter work happening in somebody else's repository.

One VRF per partner

The cloud-router estate gives every roaming partner its own VRF, its own bridge on the tanker, and a GRE tunnel to each router in the pair (two routers, so two tunnels per VRF). A partner's name appears four times in a site file: the VRF, the bridge, the Docker network, the tunnel list. Nowhere else. The isolation is the VRF itself, so there is no shared peering segment to police (and no per-partner firewall policy to maintain).

Inside a partner's VRF sits a short list of containers, and the names say what the integration is made of.

VRF_WL_PARTNER_B:
  bridge_subnet: "172.22.9.0/24"
  preset_containers:
    - name: "partner-b-proxy"
      ip: "172.22.9.2"
      apply_net4_rfc1918_filter: false
    - name: "wireless-dra-partner-b"
      ip: "172.22.9.52"
      apply_net4_rfc1918_filter: false
    - name: "wireless-apn-dns-partner-b"
      ip: "172.22.9.62"
      apply_net4_rfc1918_filter: false

A proxy, a Diameter routing agent, an APN DNS resolver, and an address convention holding them apart (.1 to .50 for the application vendor, .51 to .60 for DRA, .61 to .70 for DNS). That convention is written as a comment above the list, and the comment is the only place it exists.

What I did and did not do

My commits allocated the addresses those containers bind to, peering and non-peering, in two production sites. That took about eight months. CW-1645 added the Partner A and Partner B DRA addresses in EU Central and then in US East (two commits, one per site). CW-1693 did the same for the two partners' DNS servers; CW-2213 added the signalling transfer points on both sides. The DRA and the APN DNS service live in separate repositories with separate owners, and I wrote neither.

That division matters for a dull reason. An address allocation can be wrong in exactly two ways — it collides, or it is in the wrong VRF — and neither one looks like a Diameter problem when it breaks.

The entry that was in the wrong VRF

CW-2256 moved a vendor's session-management function in US Central, and the entry it deleted is the tell.

    - name: "vendor-ngc-pgw-dataplane"
      ip: "<shared-space>.125/24"
      apply_net4_rfc1918_filter: false
    - name: "vendor-ngc-smf"
      ip: "<shared-space>.116/24"

The second entry has no third line (two lines, where every sibling has three). Every other container in every site file carries apply_net4_rfc1918_filter: false, so the router applied its default RFC1918 ingress filter to that one interface — on a bridge in shared address space (100.64/10) that carries private traffic. The fix deleted the entry and re-added the function in the Partner C breakout VRF, flag set, at 172.22.177.116/24. One absent line, in a list of three-line entries, in a 686-line file.

Two things in that file resist automation

The address notation is inconsistent: EU Central entries are bare addresses (172.22.9.2) while US Central ones carry a prefix length (172.22.177.116/24). Both forms work, so nothing ever corrects them (the module accepts either). The group directory for US Central used underscores (wireless_site-a_prod_1) where the other five sites used hyphens, and that was normalised later, by someone else, in a rename commit.

What it cost

Thirty-three commits over eight months, nearly all of them edits to one YAML key in one of four site files (US Central, US East, EU Central, APAC). No protocol translation, no AVP rewriting, no per-partner certification profile, no connection pooling — the routing layer has no idea Diameter exists, and the parts that do are deliberately somewhere else. The only interesting engineering at this layer is the bookkeeping, and the bookkeeping is a comment block.
