Three IMS services, one image, and a meta file that keyed the wrong name

The IMS components in our deploy repo took two attempts ten months apart, and what broke the first one was which name goes in the image key.

Infra

What these services are

Four services in the deploy repository carry ims in the name (cscf, dns, mysql, dra). Three of them are one build — the CSCF image, tagged per component. So a DNS deploy asks for image wireless-ims-cscf at version wireless-ims-dns-2025.04.15.07.37.652f199, and the component lives in the tag instead of the repository name. The DRA is a separate C++ service from another repository entirely.

None of this is Kubernetes (no pods, no overlays, no ArgoCD application). All four run as Docker containers on bare-metal hosts driven by Ansible, one instance each, with 256 CPU shares and 256MB of memory, and the CSCF, DNS and MySQL all land in the same host group (wireless_ims_prod). The dev meta files carry tankers_use_deploy_role: false, which selects the legacy deployment mode the old pipeline used.

The first attempt, and the day it lasted

April 2025, for the DNS and MySQL pair (two services, four files). The meta files keyed service_images by the service name with an explicit registry path:

service_images:
  wireless-ims-dns:
    image_ref: registry.internal/jenkins/wireless-ims-cscf:wireless-ims-dns-2025.04.15.07.37.652f199

That is wrong in a way that reads correctly. The key names the image, not the service, and the generator resolves the registry path itself from the version string. Four commits the same afternoon chased it (correct image names, a bug fix in the meta files, the deploy role for prod, then the key), ending at the shape that works: key wireless-ims-cscf, value a plain version, the broken line left commented out above it as a note to the next person.

One of those files had wireless-admin as the image key — copy-paste from the service directory next door, and the kind of mistake a schema validator catches and a human reviewer does not.

The next day all of it came out: both services deleted, 152 lines across 8 files, including the orchestrator-generated deployed-meta.yml for dev and prod. The commit message says why — the monorepo is the only way to go. Splitting one image into separately versioned deploy-repo services was describing a build nobody produces.

The second attempt

February 2026, under a single onboarding ticket, the same three services landed again with the CSCF alongside them. All three were pinned to one version (2026.02.11.07.55.7796894), one host group per environment, and the deploy moved off the Jenkins pipeline instead of sitting beside it. That commit generated 28 new workflow files and updated 2; the configuration is a dozen lines per service (names, deploy block, host group).

Nothing about the second attempt was cleverer. The difference is that three services now describe one image at one version, which is what the build actually produces.

The part still missing

None of the four IMS services has an alerts: section in meta-prod.yml. That gap is mine, and I found it the hard way: a production host running the IMS DRA went down three times in 48 hours (55 minutes, 55 minutes, then five hours) and paged nobody. The dashboard showed nothing, and no rule existed to fire.

The HSS side of the same estate was easier, because the probes already existed and had to be re-pointed. Migrating the Diameter and M3UA probe set to the replacement HSS meant rebuilding the probe list from the new platform's association table (Diameter on 3868, six M3UA associations on 2905-2911, two more on 8449) and deleting the old host's config: 172 lines out, 94 in.

Four services, one image, and an alert catalogue that is still empty. The first of those took two attempts; the last one is still open.
