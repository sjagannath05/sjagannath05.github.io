Ten scrape jobs and one transposed digit

A batch of static scrape targets, the typo that went in with them, and why nothing in the pipeline could have caught it.

DevOps

The change

Ten HSS and SMSC instances across two sites (five pairs in all) needed to appear in Prometheus. These are vendor appliances, so there is no exporter to install and no service discovery to join — the application serves its own metrics, on its own path, and the only way in is a static target (one address, typed by hand):

- job_name: 'hss_prod_site_c_01'
  metrics_path: '/hss/prometheus'
  scrape_interval: 1m
  scrape_timeout: 1m
  static_configs:
    - targets:
      - 172.22.39.2:8090

Ten of those, one per instance, split between two overlay files (six at one site, four at the other) under a single ticket. The path is /hss/prometheus and not /metrics, the port is 8090 and not 9100 (node_exporter's default); both facts come from the vendor, not from any convention in the repository. Each site runs the pair together, HSS on .2 of its subnet and SMSC on .3, which is the pattern that makes the whole file skimmable — and the pattern that hid the mistake.

The transposed digit

The second instance at one site sits on 172.22.42.0/24. Its HSS went in as 172.22.42.2 and its SMSC as 172.22.43.3 — right last octet, wrong subnet. A one-line follow-up commit in the same pull request fixed it to 172.22.42.3 (one character, same day, same pull request).

What is worth noticing is everything that did not fire. The YAML was valid, so the parse succeeded. Kustomize rendered it (no schema for target addresses), so the build succeeded. Prometheus loaded it, because a target that will never answer is still a well-formed target. The review passed, because 43.3 next to 42.2 reads as a plausible pair when every other line in the diff looks the same. There was no stage between commit and production whose job was to find this.

The one signal that exists is up. A static target that answers nothing reports up == 0 for its job, forever, from the first scrape (no retry, no backoff, no escalation). That is a complete detection mechanism and it is also entirely passive — it tells you only if somebody looks, and the person most likely to look is the person who just added the job.

The same mistake in a different shape

A year earlier a single-VM scrape job (one target, port 19100, node_exporter this time) went into one cluster's scrape config and then moved out of it, into a second cluster that sits closer to the service being scraped; the job name lost its underscore for a hyphen in the same change (<svc>_vm to <svc>-vm), for consistency with everything around it. Same target, same port, same interval (1m, like everything else) — wrong location, and the correction was a second commit, not a review comment.

Two instances of the same class of fault, a year apart. A static target carries facts that only the person who owns the appliance knows (address, port, metrics path, subnet), and no amount of templating validates any of them. The repository can check that your YAML is YAML. It cannot check that .3 is in the right /24.

What would have caught it

Something that compares intent against reality: generating the targets from the address management system that already records them, or alerting on up == 0 for a newly added job by default. The first removes the hand-typed octet; the second makes an existing signal active instead of passive (one rule, scoped to new job names). Neither existed, and both were out of scope for a ticket whose whole content was "add scraping targets".

So the honest version is small. Twelve scrape jobs over fourteen months (four pull requests, two sites), one of them wrong for an afternoon, caught by the person who wrote it and fixed in the same pull request. The repository that held all of it was deprecated in May 2026 and the targets moved elsewhere.
