Four sites, six site files, and no cross-site anything

Every region in the cloud-router repository is described in isolation, and the tunnel count inside one of them grows as VRFs times routers.

Infra

Every region in the cloud-router repository is described in isolation, and the tunnel count inside one of them grows as VRFs times routers.

What a region is here

Six wireless site groups existed when I was working in this repository, and I touched four of them (US Central, US East, EU Central, APAC). The other two (a dev site, and a second Asia-Pacific site) I never had reason to open.

A "region" here is not an AWS region (the word is doing two jobs). The first five lines of every site file say what it actually is. A site code, an environment, a Consul datacentre, the AWS VPC, and the colocation cage in the same metro that the VPC cross-connects into. Everything else hangs off one key with seven sections: the cluster, the virtual routers, the tankers, the router pair, the VRF definitions, and two separate link tables (one for router-to-router, one per VRF).

What the file does not have is any reference to another site. No peer list, no transit configuration, no failover block — nothing at all. Cross-site traffic is carried by containers called intersite proxies. They appear in these files the way any other container does (a name, an address, a filter flag). Two of my commits (CW-2188 in EU Central, CW-2205 in US East) are two lines each, and that is the entire footprint of inter-region routing in the repository.

The tunnel arithmetic

Each tanker reaches each virtual router through a GRE tunnel, and it needs one tunnel per VRF. So the tunnel count on a tanker is VRFs times virtual routers (six VRFs and two routers gives twelve), and the link table grows as a product while the estate grows as a sum.

- vrf_name: "VRF_WL_PARTNER_B"
  vclr: "vclr01"
  vatr: "wireless-02"
  gre_id: "gre5204"
  gre_vclr_ip: "169.254.66.136"
  gre_vatr_ip: "169.254.66.137"

Two conventions are doing real work there (both undocumented). Tunnel IDs beginning 5 belong to the first virtual router and those beginning 6 to the second, so an ID tells you which side of the pair you are on. The link-local addresses are handed out in consecutive pairs from one /24, so a gap in the sequence means a tunnel was removed and the block was never reclaimed.

By May 2025 the EU Central file held four virtual routers and thirty tunnels (443 lines in all). None of that is hard. It is simply impossible to keep correct by reading.

The APAC tanker that carried nothing

CW-1256 is the one commit here I would defend as engineering. One tanker in APAC had six VRFs defined, bridges for all six, and twelve GRE tunnels — and preset_containers: [] on every single one of them. Twelve tunnels and six bridges existed for zero containers — the whole VRF fan-out, serving nothing.

The cleanup took the five unused VRFs off that tanker and deleted ten tunnels with them, leaving one VRF (the core one) with a resubnetted bridge. The site file went from twenty-eight GRE tunnels to eighteen — a third of the link table, for one tanker.

It was a half cleanup, and worth saying so plainly. The six VRF definitions at site level survived, because they are shared with the other tanker; only the bridges and the links went. And the change followed reality instead of leading it. A commit from the infra team in the same pull request is titled "update repo with manual VRF changes made in the tanker" — the box had already been cleaned by hand, and the file was catching up.

What is not in these files

No transit gateway, no dedicated interconnect, no link encryption, no failover timers (and no regional on-call structure). The repository renders router configuration for one site at a time, and the only thing tying the sites together is a naming convention and a pair of proxy containers. Treating that as a global architecture would be flattering it; treating each file as a long, unverified list is closer to the truth, and explains why the interesting bugs are all bookkeeping.
