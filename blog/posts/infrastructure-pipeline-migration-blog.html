Three lines of Jenkinsfile, and four hours finding them

Replacing a 117-line pipeline took one commit; deciding where the rolling dev tag lives took five.

Infra

Replacing a 117-line pipeline took one commit; deciding where the rolling dev tag lives took five.

What arrived with the fork

The service is an Elixir/Phoenix PCAP extractor the wireless squad forked from a Telephony-squad tool. The application is a colleague's work — the primary_maintainer line in meta-dev.yml is my own commit saying so — and every commit of mine in the repository is on the build or the deploy. CW-1479 was the ticket: take it off the Telephony ansible path and onto the shared wireless pipeline.

The Jenkinsfile it came with ran 117 lines of declarative pipeline across five stages (Build, Validate build, Push to registry, Deploy, Postbuild), each one gated on a changelog regex for [ci skip]. Its deploy stage triggered a downstream ansible job by name and passed hosts: 'pcap_extractor:&dev'. The replacement is three lines:

@Library("infra-ci-pipelines@latest") _
ciPipeline {
    service = "wireless-pcap-extractor"
}

That build failed on the first run. mix hex.organization auth needs the private hex key, which the old pipeline had bound from a Telephony credential, so three string credentials went back in by hand (ELIXIR_HEX_KEY, ELIXIR_OBAN_KEY, ELIXIR_OBAN_PUBLIC_KEY_FINGERPRINT).

Where does the dev tag live

The shared library has two entry points and I used both before settling. ciPipeline builds and deploys from meta-dev.yml; dockerImage only builds and pushes, leaving deployment to a separate deploy repository. The commits, in order on one evening (19:45 to 23:59):

  • ciPipeline, then dockerImage with VERSION rewritten from 1.0.0 to red
  • VERSION back to 1.0.0, with image_additional_tags = ["red"] instead
  • image_additional_tags dropped for a new one-line IMAGEVERSION file holding red, plus use_version_file: true and version_file_path: IMAGEVERSION
  • back to ciPipeline, deploy stanza restored

The answer turned out to be two files, not one. VERSION carries the semver the application compiles against (app_version.exs reads it, and falls back to git describe with a warning when it is absent), and IMAGEVERSION carries the tag the pipeline pushes. Putting red in VERSION made every build report its version as red.

Jenkins to Actions, eighteen months later

CW-3385, 12 February 2026. The Jenkinsfile (9 lines by then) and a semgrep.yml (23 lines) were deleted, and a 17-line workflow replaced both:

jobs:
  docker-image:
    uses: infra-ci-gha-workflows/.github/workflows/dockerImage.yml@latest
    secrets: inherit
    with:
      image_additional_tags: red

Credentials moved from Jenkins credential IDs into vault references, and the obvious shape was the wrong one. A list of {path, key, env} objects is what the YAML wants to be; the pipeline reads a single string, one <path> <key> | <env> per line, semicolon-terminated. The vault path changed spelling at the same time — core.wireless.squad/data/provided_creds became core-wireless-squad/data/provided-creds, dots and underscores to hyphens.

Three commits that afternoon (migration, secrets format, then allow_vulnerable_image: true because the image scan failed the build). promote_to_prod: mode: always landed three hours after that, so an image that passes in development is promoted instead of rebuilt — which matters because a rebuild is a different image.

What it cost

About twenty commits: one evening in August 2024, one afternoon in February 2026. What the repository has to show for it is a 17-line workflow, no Jenkinsfile, and a Makefile that seeds its own build cache with docker pull $(docker_image) || true so a missing previous image cannot fail the build.

Neither migration moved production. The container needs host volumes mounted for the pcap directories, so deployment stayed on the legacy ansible route in both environments, and the pipeline work only ever covered build and promotion.
