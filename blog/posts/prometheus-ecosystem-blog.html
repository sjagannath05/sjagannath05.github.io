The Prometheus stack, split three ways: what I configured, what I operated, what the software does

An honest accounting of a monitoring stack, because "I worked with Prometheus, Alertmanager and Thanos" hides three very different claims.

An honest accounting of a monitoring stack, because "I worked with Prometheus, Alertmanager and Thanos" hides three very different claims.

Why the split matters

Most writing about the Prometheus ecosystem blurs three things together: configuration someone authored, a service someone operates, and behaviour that is simply how the upstream software works. The third category is the largest by far, and it belongs to the Prometheus authors — describing it in the first person is the most common way a monitoring post becomes fiction.

So here is my own stack, sorted.

What I configured

Scrape jobs, and only scrape jobs. Across four pull requests (December 2024, April 2025, July 2025, February 2026) the surface I touched is narrow enough to list exactly:

  • job_name, metrics_path and static_configs targets — including one application whose exporter answers on /hss/prometheus instead of /metrics, which is the kind of detail no service discovery will guess for you.
  • scrape_interval and scrape_timeout, both at 1m for every job I added (all twelve jobs I added use exactly that pair). One went in wrong — 30s interval, 2m timeout — and Prometheus refused the whole file, not just the job.
  • honor_labels, flipped from false to true on a /federate job so the federated samples kept their own job and instance.
  • params: match[] on that same federate job, set to {__name__=~".+"} — everything the collector holds.
  • relabel_configs, four rules, moving job and instance aside into secondary_* labels (one of the four reads a label that targets do not carry yet, so it does nothing).

That is the list. It does not include a single alerting rule, recording rule, Alertmanager route, Thanos setting or Grafana dashboard — I touched five files in that repository over fourteen months (three scrape configs, the changelog, and one duplicate of a scrape config in a second cluster).

What I operated

Operating something leaves no commits, and it is still real work. The Prometheus servers, Alertmanager and the Thanos components were run by the infrastructure team; I used them. That means querying for a target that stopped answering, reading up for a job I had added (the only check that tells you a static target resolved), checking whether an alert I cared about had fired, and watching application state through Argo CD — checking sync status, reading logs, resyncing when something had drifted, redeploying. None of that is authorship. All of it is daily.

The distinction has a practical edge: an operator notices different faults from an author. A static target with a transposed digit is invisible to the person who wrote the templating (the YAML is valid, the render succeeds) and obvious to the person watching up for that job.

What the software does

Everything else, and it is worth separating out because it is the part readers actually want explained.

Prometheus pulls. A server scrapes HTTP endpoints on a schedule, stores samples in a local time-series database (local disk, not a cluster), and evaluates rules over them; it never receives pushes, which is why every integration question reduces to "what URL, how often, and which labels". honor_labels exists because a pull model creates a collision the push model never has — the scraper has an opinion about the target's identity and the target may have its own.

Federation is Prometheus scraping Prometheus. The /federate endpoint serves a selected subset of one server's series to another, and the selection is yours (match[]); the semantics are upstream.

Alertmanager deduplicates, groups, silences and routes; Thanos adds object storage and a global query view across servers (sidecar on each server, store gateway for history). Both solve problems that appear at a scale above a single server. I configured neither, and saying otherwise because they were in the same repository would be a lie of adjacency.

The test

For any claim in a post like this, ask what artefact would show it. A commit, a config block, a ticket, a dashboard with your name on the panel. For the operating claims, there is no artefact, so say "operated" and let the reader weight it. For upstream behaviour, cite the docs and use the third person.

Four pull requests, twelve scrape jobs, one repository that was deprecated in May 2026 (nine removal commits, one day). That is a smaller claim than the stack's name suggests, and it is the one I can back.
