A service name is not an architecture

`wireless-pwg-dns` reads like DNS infrastructure for a wireless core; it is a pinned base image, a tag, and a list of owners.

Infra

wireless-pwg-dns reads like DNS infrastructure for a wireless core; it is a pinned base image, a tag, and a list of owners.

What the name promises

Read the name and you expect zone data, a resolver topology, failover between sites, and some way for gateway instances to register themselves as they come and go — none of which is here. The README is narrower. It says the repository maintains a custom image for serving DNS to private PGWs, created mainly to expose metrics, and that it is based on CoreDNS (1.11.1, the tag the first commit pinned).

Eleven commits exist since July 2024, eight of them on a single afternoon (11 February 2026). The eight files are a Dockerfile, a Makefile, two meta files, a VERSION, a README, a one-line changelog and two workflows. The service discovery, high availability and mesh integration described in the earlier version of this post were never committed anywhere, because they were never built.

The scan has nothing to read

on:
  pull_request: {}
  schedule:
    - cron: '28 4 * * 0'

.github/workflows/semgrep.yml runs semgrep ci on every pull request and again weekly (Sundays, 04:28 UTC). For pushes it is path-filtered to the workflow file itself, so only a change to the scan's own definition triggers it on a push.

Static analysis here has two Dockerfile lines (FROM and EXPOSE), nine lines of Makefile, and some YAML to look at. There is no application code — the application is upstream, and arrives as a digest.

That is an observation, not a complaint. One uniform scan across every repository (one policy, no exemption list) is cheaper to run, and the day somebody adds a plugin or an entrypoint script it is already wired in.

Where the risk sits

The security surface of a service like this is the upstream tag, and the set of people who can merge to main (two decisions, both human). VERSION holds the CoreDNS release itself (1.11.1, no independent numbering), so every bump is an upstream bump and the changelog stays one line long. No linter will tell you whether 1.11.1 is still the right pin; that answer comes only from release notes and the clock.

Zone data, resolver placement, and whatever answers when a gateway asks: all of it is deploy-time configuration, held outside this repository by the teams that own those layers. I pinned a base image, wrote down a port (11915/tcp, clear of everything else on the host), and named two maintainers. The honest claim is narrower than the service name, and considerably duller. The gateways pull their resolver from an internal registry at a known version — and its metrics come out where everything else's do.
